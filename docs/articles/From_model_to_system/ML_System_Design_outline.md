# От Jupyter Notebook к промышленной ML-системе

Почему 90% моделей никогда не становятся промышленными решениями

## Введение

История большинства ML-проектов выглядит одинаково.

В Data Science отделе появляется Jupyter Notebook.
На тестовых данных модель показывает Accuracy 96%.

Через несколько месяцев оказывается, что модель так и не используется в бизнесе.

Почему?

Потому что модель — это всего лишь одна небольшая деталь системы.

Настоящая ML-система — это десятки сервисов, сотни архитектурных решений и огромное количество инженерных компромиссов.

В этой статье мы пройдем путь от первого ноутбука до промышленной AI-платформы глазами архитектора.

## Этап 1. Jupyter Notebook

- Цель этапа
- Роль архитектора
- Типичные ошибки
- Когда пора переходить дальше

Что существует

- Есть ноутбук.
- Есть данные.
- Есть обученная модель.

Все работает.

CSV
   ↓
Pandas
   ↓
Notebook
   ↓
Model

Задачи архитектора

На самом деле архитектора пока нет.

Главная задача — доказать, что идея вообще работает.

Это стадия исследования.

Основные ошибки

- Пытаться проектировать Enterprise-архитектуру до появления первой модели.
- Игнорировать воспроизводимость экспериментов.

Через неделю уже невозможно понять:

- какая версия данных использовалась;
- какие параметры обучения были;
- какая модель дала лучший результат.

Следующий вызов

Ноутбук умеет обучать модель.

Бизнес хочет получать прогнозы автоматически.

Появляется первая архитектурная задача.

## Этап 2. Первый сервис инференса

- REST API
- Контейнеризация
- Версионирование моделей
- Контроль схем данных

Notebook
      ↓
Saved Model
      ↓
REST API
      ↓
Application

Что изменилось - Теперь модель должна отвечать на запросы.

Она становится частью продукта.

Задачи архитектора

Необходимо решить:

- как сериализовать модель;
- где она будет храниться;
- как загружаться;
- как обновляться;
- как масштабироваться.

Появляются:

- FastAPI
- MLflow
- Docker

Главные ошибки

- Модель загружается на каждый запрос
- Нет контроля версии модели
- Нет контроля схемы входных данных
- API ломается после первого обновления модели

Следующий вызов

Модель работает.

Но как ее переобучать?

## Этап 3. Автоматизация обучения

- Training Pipeline
- Registry
- CI/CD для ML
- Воспроизводимость

Появляется pipeline.

Data
 ↓
Validation
 ↓
Training
 ↓
Evaluation
 ↓
Registry

Архитектурные задачи

Архитектор начинает думать уже не о модели.

Он проектирует процесс.

Появляются вопросы:

- кто запускает обучение;
- когда запускать обучение;
- как откатывать неудачные версии;
- как хранить артефакты;
- как воспроизводить обучение.

Главные ошибки

Обучение запускается вручную.

Никто не знает:

- какая модель сейчас используется;
- почему именно она;
- можно ли повторить обучение.

## Этап 4. Данные становятся системой

- Data Platform
- Feature Store
- Data Quality
- Data Contracts

До этого данные были “файлом”.

Теперь это полноценная инфраструктура.

Sources
 ↓
ETL
 ↓
Feature Store
 ↓
Training
 ↓
Serving

Новые задачи архитектора

Самая большая проблема ML — не модель и не данные.

Необходимо обеспечить:

- единые признаки;
- отсутствие data leakage;
- одинаковую обработку train/inference;
- контроль качества данных.

Главные ошибки

Feature Engineering реализован два раза.

Один код — для обучения.

Второй — для продакшена.

Через месяц модели начинают расходиться.

## Этап 5. Появляется Production

- SLA
- Масштабирование
- Kubernetes
- Безопасность

Теперь модель используется пользователями.

Возникают новые требования.

Users
 ↓
API Gateway
 ↓
Model Service
 ↓
Monitoring
 ↓
Logs

Задачи архитектора

Теперь появляются вопросы:

- SLA;
- отказоустойчивость;
- масштабирование;
- балансировка;
- безопасность.

Ошибки

Архитектор думает только о модели.

На практике система падает потому что:

- закончилось место в очереди;
- Redis переполнен;
- API не выдержал нагрузку;
- Kubernetes пересоздал Pod.

## Этап 6. Monitoring

- Model Drift
- Data Drift
- Concept Drift
- Бизнес-метрики
- Observability

Теперь нужно понять — модель вообще работает?

Контролируются уже не только серверы

Теперь необходимо измерять:

- качество модели;
- drift;
- data drift;
- concept drift;
- распределение признаков;
- задержки;
- стоимость инференса.

Главная ошибка

Следить только за CPU и RAM.

Модель может работать идеально… но ее качество уже упало в два раза.

## Этап 7. Continuous Learning

- Автоматическое переобучение
- Canary Deployment
- Shadow Deployment

Модель постепенно устаревает.

Необходимо организовать цикл жизни.

Production
 ↓
Monitoring
 ↓
Retraining
 ↓
Validation
 ↓
Canary
 ↓
Production

Вопросы архитектора

- Как понять, что пора переобучать?
- Как сравнить новую модель со старой?
- Как безопасно переключить пользователей?
- Как откатиться назад?

Ошибки

- Переобучение “по расписанию”.
- Без понимания, стало ли лучше.
